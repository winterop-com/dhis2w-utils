## Unreleased

- **The Forms page groups by capture model, not by table row** (2026-08-11). `/#/forms` rendered a data set, an event program, and a tracker stage as equal rows of one flat table, which is exactly the dependency it hid: a stage form is not a standalone capture surface. The page now reads as sections by what a thing is - **Data sets** ("Periodic reports for an organisation unit. Every row keeps its click-to-open, question count, and mono id; the per-row kind badges are gone, because the section heading states the kind once and the role notes carry the tracker split - a form declaring no `D2FormType` gets its own stated section rather than a badge, since the facade refuses to capture against it. Empty sections are omitted, not rendered empty. The fold is `catalogueForms` in `lib/catalogue.ts` - the organisation-units rail's grouping lifted into lib and reused by both pages, so the two listings can never disagree about what a form is - proven by vitest over the harvested fixtures (both tracker shapes: a program with a published registration, and a stage served alone) and by the rewritten Playwright forms spec (section headings, registration-then-stages order, the dependency line, click-through).

- **Serve audit fixes: distinct unique answers, seeded unit draws, HEAD parity, honest refusals** (2026-08-10). Four end-to-end audit findings against `d2w fhir serve`, each held by tests.

    **`$generate` answers a unique attribute the way the load set does.** A `unique` tracked entity attribute was answered with a constant string, so every generated registration of a form carried the same business identifier and DHIS2 imported exactly one of them (`E1064` for the rest). The capture index now reads the attribute support CodeSystem's own concept properties - `value-type`, `unique`, and the display - and the synthesizer answers a unique question through the very rule the examples emitter uses (`distinct_unique_value`): the value embeds the response's own minted tracked-entity UID, spelled the way the attribute's value type admits. A value type with no room for a distinct value, a bounded integer, or a store serving no attribute pair keeps the ordinary draw, because generating outside what the form admits would break the post-back invariant.

    **The organisation unit is part of the seeded draw.** `$generate` reported every response for a deterministically-fixed Location - the first of the assignment, else the first served. The unit is now drawn from the seed like every other value, across the whole admitted set: the form's published assignment (intersected with the served registry so the unit really exists; the whole assignment stands when the store serves none of it), the whole registry when the form publishes no assignment, and the shaped-UID fallback when the project published no registry at all. Same seed, same unit; different seeds range over the set; the 201 post-back invariant holds under `--strict-codes` because every draw stays inside the assignment DHIS2 would check with `E1029`.

    **HEAD answers wherever GET does.** FHIR liveness probes ask `HEAD /metadata`, and the facade answered 405 - FastAPI registers only the methods a decorator names. Every GET route now takes HEAD too, applied as one sweep over each router at mount time, so `/metadata`, reads, searches, and the operations all answer the probe; verified against real uvicorn, which sends the headers and withholds the body.

    **A wrong Content-Type is a 415, and a diagnostic never says `None`.** A `POST /QuestionnaireResponse` declared as `text/plain` was parsed as if nothing had been said; it now answers 415 with an OperationOutcome naming the media type, while `application/fhir+json`, `application/json`, any `+json` type, and an absent header keep working. And a body naming no `resourceType` was told "not a `None`" - Python's spelling of absence interpolated into a diagnostic. The refusal now says the element is missing, and the other interpolations that could leak a `None` (a subject or enrollment identifier without a system, a period range without a bound) state the absence in words.

- **A stage form answers for a real enrollment, chosen on the form** (2026-08-10). The capture UI's tracker stage forms carried the `$generate` skeleton's synthetic tracked-entity and enrollment identifiers into every submission - a pair that names nothing in any DHIS2, so every unassisted stage capture was refused at forward time (`E1079`/`E1313`: the enrollment does not exist). The real pairs are in the facade's own spool: a stage form names its program on the `{base}/id/program` identifier, the program's registration form carries the same identifier as its own identity, and every receipt answering that form holds one minted pair. The form-fill page now joins the three and puts an "Answering for" picker beside the reporting-unit control, offering exactly those enrollments - each labelled with its uid, its enrollment date (read off the stored receipt, since the spool listing never derives `D2EnrolledAt`), and its lifecycle: forwarded means DHIS2 holds the pair, received means it will only after `d2w fhir forward` runs, and a received choice says so inline rather than at rejection time. Rejected registrations are never offered - their pair names nothing and no forwarder run will change that. The default is the newest forwarded registration's pair, so an ordinary submission lands; with nothing to offer the synthetic draw stands and the page says what that means, linking to the registration form to capture first. The choice rewrites the envelope the same replace-in-place way the attribute option combo and the reporting unit do - `subject.identifier` and the `d2-tracker-enrollment` extension value, the envelope's spellings winning, the form's own identifiers as the no-envelope fallback - and it survives "Fill with test data" by the opposite merge rule from its two neighbours: a fresh draw's answers pour in, but adopting its freshly minted synthetic pair would replace a real enrollment with uids that name nothing, so the identity stands. The offer reloads on window focus like the spool listing, for the same reason: the forwarder is another process, and a received badge should catch up when you come back from the terminal.

- **The default category is a placeholder, not terminology** (2026-08-10). DHIS2's built-in `default` category means "no disaggregation was entered" - it exists on every instance and exchanges no information - yet the categories target published it as a CodeSystem/ValueSet pair titled `default`. `[generate.categories] include_default = false` (the default) now keeps it out of every path that applies the selection: `generate categories`, `generate full`, and `serve --live` emit no CS, no VS, and no ConceptMap for it, and `d2w fhir validate` resolves its categories scope through the same predicate, so the ignored object grades as instance hygiene rather than build impact and leaves the code-coverage denominators. An `include_ids` entry naming its UID overrides the flag - the most specific configuration statement wins - and `include_default = true` restores the previous output byte for byte. Detection is the reserved name: `/api/categories` carries no `isDefault` flag (categoryCombo and categoryOption do), and DHIS2 hardcodes and rename-protects the default category's name as exactly `default`, so the match is case-sensitive on that spelling and a user category named `Default` is a category like any other. The default category option combo needed no governing: only non-default combos contribute option combos to `D2COC_CS`, so it structurally never surfaces there, which a test now states.

- **A dictionary concept states the DHIS2 code it has, and no code it does not** (2026-08-10). The data dictionaries wrote `dhis2-code` on every concept, falling back to the object's UID when DHIS2 held no code - which published the UID twice, once as the concept code it truthfully is and once under a label saying it was the object's DHIS2 code. Verified live: `Gender` and `Last name` carry no code in DHIS2 at all. The property is now written only where DHIS2 states a code, and declared only where at least one concept carries it - the rule `domain` and `value-type` already followed. `D2DE_CS` also publishes **real** data-element codes for the first time: `code` joins the data-element projection the questionnaire fetch already reads, at id-only cost, so the data-element half stops being a column of UIDs. Both emit paths, parity held, goldens recompiled with SUSHI.

- **Sentence-case terminology titles** (2026-08-10). `DHIS2 Data Elements`, `DHIS2 Tracked Entity Attributes`, `DHIS2 Category Option Combos`, `DHIS2 Organisation Units`, and `DHIS2 Organisation Unit Levels` were title-cased while every foundation pair beside them (`DHIS2 form types`, `DHIS2 period types`) was not. All five are sentence case now, which is what the rest of the published prose reads as. The two profile titles that name a FHIR resource type keep their capital - `DHIS2 Location` and `DHIS2 Organization` are the resource types, not prose.

- **A registration answer knows which DHIS2 level it belongs to** (2026-08-10). DHIS2 asks a tracker registration's questions at two levels, and the import endpoint keeps them apart: an attribute of the program's **tracked entity type** is stated on `trackedEntities[].attributes`, an attribute only `programTrackedEntityAttributes` names on `enrollments[].attributes`. Every registration answer went onto the tracked entity, which the demo programs never punished - their attributes are all on their type as well - and a genuinely program-only attribute would have been refused at the entity level.

    **The level rides the program fetch already paid for.** `trackedEntityType[id,trackedEntityTypeAttributes[trackedEntityAttribute[id]]]` folds into the read the registration form is built from, so knowing which attributes the type collects costs no extra request. The questions themselves stay the program's join - `mandatory` and `sortOrder` are per-program facts and are read where they live.

    **The guide publishes it per question, on the item.** A new foundation extension, `D2EntityLevel`, a `boolean` contexted on `Questionnaire.item`: true for an attribute the tracked entity type collects, false for one only the program asks. It sits on the item rather than as a `D2TEA_CS` concept property because the fact belongs to the attribute **and the tracked entity type together** - `D2TEA_CS` is one dictionary across every registration form of a run, and two programs on different types can honestly disagree about the same attribute, which one concept entry cannot say twice. Every other property that pair carries (`dhis2-code`, `value-type`, `unique`) is a fact about the attribute alone, and stays there. A third party converting from the compiled guide alone reads the right level per form, which is the bar the extension exists to clear.

    **The conversion splits by what the form published.** `translate_tracker_registration_response` writes the entity-level answers on the tracked entity and the program-only ones on the enrollment it creates, both through the same value-type serialisation and the same strict/lenient coded-answer dial. A question stating no level at all - a guide compiled before the extension was published - is written on the tracked entity, which is where every registration answer went before the split, so an older compiled guide keeps translating exactly as it did.

- **A load set that imports: distinct business identifiers, and a salt for the second run** (2026-08-10). The first real `--import` of a tracker corpus came back 153 accepted, 72 rejected, and the rejections were one cause wearing two error codes.

    **`E1064` x24: one invented constant is not a business identifier.** A `unique` tracked entity attribute was answered `Example Unique ID (Play)` by every registration of the program, because a synthetic TEXT value was the question's name and nothing else. DHIS2 takes the first and refuses the rest - and refuses the enrollment nested in each of them, and every stage event on those enrollments. So a corpus of 25 registrations registered one person. A unique attribute is now answered from the response's own **minted tracked-entity UID**, the one thing no other response in the corpus holds, spelled the way its value type admits: textual types embed it, `EMAIL` / `URL` / `PHONE_NUMBER` take it in their own shape, and the integer family derives a nine-digit number on whichever side of zero the type allows. A value type with no room for it - a boolean, a `LETTER`, a date, an option-bound attribute - keeps its ordinary draw and is **named in a note**, because inventing a value outside what the type admits to dodge a duplicate would trade a refusal that can be explained for one that cannot. Regenerated against the instance that produced the failure: 25 answers, 25 distinct, and 23 of the 24 previously-refused registrations now validate clean (the 24th only because it already exists from the run that exposed this).

    **`E1079` x48 was that same failure, wearing a misleading code.** The message says the event's program differs from its enrollment's, which reads as a cross-program mix-up in the identity threading. It was not: all 48 were the stage events of the 24 registrations `E1064` had refused, and DHIS2 raises `E1079` (plus `E1313`) for an enrollment that does not exist at all rather than the `E1081` it has for exactly that. Verified by matching every enrollment named in an `E1079` against the enrollments those refused registrations minted - 24 of 24 - and the threading is now pinned by a regression test that builds **two** tracker programs and asserts every event's `(trackedEntity, enrollment)` pair comes from its own program's registrations. Logged as BUGS.md #68, because the code sent a reader looking in the wrong module for a cycle.

    **And a corpus imports once, which is now said out loud.** It mints the DHIS2 identities it names, so re-importing the same corpus is refused on the identities themselves - `E1002` for the tracked entity, `E1080` for the enrollment - whatever the values say, because `importStrategy=CREATE` means create. Confirmed twice against the live instance. Salting only the unique values would have fixed nothing, so the knob is a run salt: `d2w fhir generate load-set --salt <anything>` moves every seeded draw at once into a genuinely different corpus, and the same salt reproduces it exactly. An unsalted run hashes the material it always did and stays byte-identical.

- **A tracked entity is not always a person** (2026-08-10). DHIS2 tracks herds, water points, buildings, vehicles, and lab samples through the very same registration-and-stages shape it tracks patients through - and every generated tracker form said `subjectType = #Patient` regardless. `[generate.tracked_entity_types]` is where a project says what its tracked entity types really are: a map of tracked entity type UID to FHIR resource type, one of `Patient`, `Person`, `Practitioner`, `RelatedPerson`, `Group`, `Device`, `Location`, `Organization`, or `Specimen`, and anything else refuses the config by name rather than mis-typing every form of a program.

    **Keyed by tracked entity type, not by program.** The type is what owns the nature of the thing, so two programs tracking one type agree by construction and neither can be configured into disagreeing with the other. A program's registration form and every stage form of that program read the same entry, because a stage captures a visit by the very entity the registration enrolled.

    **One resolution, every consumer.** `form_subject_type` is the single call: `Questionnaire.subjectType` on both emission paths, the `subject.type` of the example responses on both paths, and the reference targets the two tracker response profiles admit. A response profile is published once for the whole IG and cannot pin one program's type, so it admits the union of `Patient` and every type the project configured - `Reference(Patient)` for a project that maps nothing, `Reference(Patient or Group)` for one that tracks herds beside people. A DHIS2 payload is untouched: the subject type is a statement about the FHIR document, and the tracked entity type the `/api/tracker` entry carries is the DHIS2 UID it always was.

    **The server reads the form, never the config.** `fhir.toml` is the generator's input and does not exist on a running facade, so the capture index carries the compiled `Questionnaire.subjectType` and both `$generate` and the capture phases read it from there. A response typing its subject as something the form is not answered about grades on the dial a drifted code and an unassigned organisation unit already ride: a warning on the receipt by default, a 422 under `--strict-codes`. `Reference.type` is optional in R4 and the profile identifies the subject by identifier, so a response carrying no type at all is complete and nothing is checked.

    **A person-tracking project configures nothing.** An unmapped type is a `Patient`, and every artifact such a project generates is byte-identical to what it generated before the table existed - which is what the tests hold first.

- **A registration is captured, converted, and posted first** (2026-08-10). The registration form shipped published and served with nothing able to answer it: `CAPTURED_FORM_KINDS` held three kinds, so the facade refused a registration response by name and the translator had no DHIS2 payload for one. It holds all four now, and everything that one tuple turns on is true.

    **What a capture server can honestly check about a minted identifier.** Its shape, and nothing else. A registration is the one contract whose DHIS2 identities the *client* mints, so the tracked entity the response is subject to and the enrollment its extension names exist nowhere yet - "does this person exist" is not a question a facade holding no instance data can answer, and for a registration the answer is meant to be no. So the envelope phase checks a DHIS2 UID shape (one ASCII letter, ten alphanumeric places) on both identifiers, one organisation unit on `D2OrganisationUnit`, and an enrolment date that reads as an R4 `dateTime`. Two things it deliberately does not check, each with a test saying so: **uniqueness**, because whether a `unique` tracked entity attribute's value is taken is global instance state DHIS2 enforces at import and a server claiming otherwise would be lying; and **whether an incident date belongs**, because the compiled Questionnaire publishes no `displayIncidentDate` - a carried one is graded on its primitive and an absent one is a complete response. The answers ride the same walk every other kind's do: value types, option bindings through the same resolvers, required questions, and the assignment dial reading the tracker kinds' organisation-unit extension rather than their subject.

    **`$generate` mints a registration too.** Seeded, deterministic, and postable straight back to the server that generated it - the 201 invariant now holds for the registration kind under `--strict-codes` as well. The incident date follows the rule the period type already follows: it is generated when a served example response answering the same form carries one, and left off when none does, because the guide's own examples are the only statement the store makes about the program. The enrolment date is always generated, because the contract requires one.

    **The payload is the tracked entity it creates.** `translate_tracker_registration_response` writes the `/api/tracker` `trackedEntities` entry: the minted tracked entity UID, the tracked entity type off the form's `$DHIS2-TET` identifier (absent, it is refused as `missing-tracked-entity-type`, because a program without one cannot register anybody), the owning organisation unit, one attribute per answered question through the same value-type serialisation and the same strict/lenient coded-answer dial a data element goes through, and the single `ACTIVE` enrollment - minted UID, program, unit, `enrolledAt`, and `occurredAt` where an incident date was stated, both read back to the zone-less wall clock DHIS2 stores. The models are the generated OpenAPI ones - `TrackerTrackedEntity`, `TrackerEnrollment`, `TrackerAttribute`, `EnrollmentStatus` - the discipline `TrackerEvent` already keeps.

    **Registrations post before events, and that is the whole of the coordination.** A client enrols a person and captures that enrollment's first stage events in one sitting, so one drain routinely holds both - and DHIS2 refuses an event naming an enrollment it cannot find with `E1313`. So a drain posts by payload kind: every tracked entity first, then everything else, each group in spool order. There is no dependency graph and no tracking of which event belongs to which registration; a registration DHIS2 rejects leaves its stage events to fail exactly as they would have, and the next run is the retry. The report still reads back in spool order, because a report is a record of the spool it drained.

    **And the load set stops being half a corpus.** Registration targets are no longer excluded, and the two halves of a tracker program agree: the registration responses mint the identifier pairs, and the program's stage responses reuse those pairs round-robin rather than inventing enrollments nothing creates. The pair is a pure function of the program UID and the ordinal, so the corpus is reproducible and every registration carries events - and since a drain posts registrations first, forwarding the whole corpus lands both halves in one run. The `E1313` wall a tracker corpus used to hit was the guide describing a capture surface it could only publish half of.

- **A tracker program becomes enrollable: the registration form** (2026-08-10). A `WITH_REGISTRATION` program had every stage published as a `Questionnaire` and no way to reach any of them. A stage is a *visit*, and nothing is captured at a visit until somebody is enrolled - which is why `d2w fhir forward` refused every tracker event with `E1313`/`E1079`: the enrollments those responses named did not exist, and nothing in the guide created them. The program itself is a form, and answering it is what enrols a person.

    **The program is the form.** One `Questionnaire` per tracker program, `tracker-programs/<program stem>/registration.fsh` beside the stage files, carrying the program's own identity - the `PR` naming token, `$DHIS2-PROGRAM` / `$DHIS2-PROGRAM-CODE`, the very pair a stage form carries as its grouping identifier - so `Questionnaire?identifier={base}/id/program|<uid>` now selects a program's whole capture surface, registration and stages together, on any FHIR server. A `$DHIS2-TET` slice names the tracked entity type it enrols a person as, which is what a client needs before it can name the person its response creates. It shares its program's assignment `List`, because DHIS2 hangs the assignment on the program, and it declares no attribute-option-combo vocabulary, because tracker capture has no third key.

    **Its questions are tracked entity attributes, typed exactly as data elements are.** The program's `programTrackedEntityAttributes` in DHIS2 sort order, through the same value-type table, the same option-set binding, the same `formName`-else-`name` text rule - `mandatory` on the join becomes `required = true` the way `compulsory` does on a stage. They get a data-dictionary pair of their own, `D2TEA_CS` / `_VS`, mirroring `D2DE_CS` concept for concept with `dhis2-code` and `value-type`, plus one property the data-element pair has no use for: `unique`, marking the attributes DHIS2 declares business identifiers rather than descriptions. **The option-set closure grew to reach them**: it was over data elements, so a set only an attribute bound would have been left unpublished with the form still binding it. It is over *questions* now, on both the generate path and `d2w fhir validate`'s scope resolution, so the two cannot disagree about what is published.

    **The response profile mints what it names.** `D2TrackerRegistrationResponse` keys the same way `D2TrackerEventResponse` does - a logical `Patient` subject identified under `{base}/id/tracked-entity`, the enrollment on `D2TrackerEnrollment` under `{base}/id/tracker-enrollment`, the capture unit on `D2OrganisationUnit` - with one difference that changes who authors those UIDs: nothing on the instance holds either yet, because this is the document that creates them, so the **client** mints both as DHIS2 UIDs. That is what lets a client enrol a person and capture the enrollment's first stage events in one breath, naming the enrollment its stage responses answer against before any of them is sent. Two new foundation extensions date the enrollment: `D2EnrolledAt` 1..1 and `D2IncidentAt` 0..1, the second `0..1` because a DHIS2 program states through `displayIncidentDate` whether it collects one at all.

    **Identifier-keyed by design.** No `Patient`, `EpisodeOfCare`, or `CarePlan` resource is published - the registration mints the identifiers and carries the attribute values, which is exactly the contract the shipped tracker-event kind already keeps. Decision 5.2 stays open: the resource layer is an addition on top of the identifier contract, not a prerequisite for it.

    **The published half.** `CAPTURED_FORM_KINDS` is the one tuple that says which kinds a server captures and a translator converts, and it is what the capture half below flips. Examples ship both ways - synthetic, and instance-sourced from `/api/tracker/trackedEntities`, one response per enrollment rather than per person.

- **The capture UI learns the registration kind: the enrollment, stated on both sides of a capture** (2026-08-10). A tracker registration is the one form kind whose whole submission is context. Its answers are tracked entity attributes, but everything that makes it a *registration* - the tracked entity uid, the enrollment uid, the date the enrollment begins, the date of the incident it follows - rides the envelope, and none of it is a question. So the browser had a form it could render and four facts it could not say.

DHIS2 scopes every data set and program to the organisation units it is assigned to, and the guide carried nothing about it - so a conformant client could build a submission DHIS2 refuses, which is what `E1029` was 202 times in the first live drain. The scope is now an artifact: one R4 `List` of Locations per form under `ig/input/resources/assignments/`, named by the Questionnaire through a single `D2OrganisationUnitAssignment` extension. A data set's List rides the `DS` naming token and its own identity stem, a program's the `PR` token and its own, and every stage of a tracker program references the program's one List because that is where DHIS2 hangs the assignment.

    **`List`, not `Group`.** A group of places is the obvious instinct and R4 forbids it: `Group.member.entity` is bound to `Patient | Practitioner | PractitionerRole | Device | Medication | Substance | Group`, and `Group.type` to `person | animal | practitioner | device | medication | substance`. A Location is neither a legal member nor a legal type, so a Group of Locations is an artifact the validator rejects. `List.entry.item` is `Reference(Resource)` and `List.mode` says `snapshot`, which is what an assignment is.

    **Absence is the common case, and it means the whole registry.** The List is written only when the assignment is a proper subset of the published organisation-unit selection, so a national form - assigned everywhere - publishes nothing at all and a consumer meeting no extension may report the form anywhere in the registry. The assignment is intersected with the published selection before it is judged, so a unit DHIS2 assigns but `[generate.organisation_units]` does not publish cannot make an assignment look narrower than it is; a form whose intersection is empty publishes an empty List and one note, because "no published unit may report this" is worth being told. The whole thing costs one id-only read per selected container, the same read `generate load-set` makes.

    **`serve` grades against it on the dial it already has.** The subject of an aggregate or event response, the `D2OrganisationUnit` extension of a tracker event, and every `ORGANISATION_UNIT` answer are checked against the form's List: a unit outside it is a warning on the receipt by default and a 422 under `--strict-codes`, exactly as a drifted code is, and the diagnostics name `E1029`. A form publishing no List, or one the facade does not serve, is checked against nothing. `$generate` draws its Location from the List when there is one, so a generated response stays postable and forwardable, and `List` joins the read/search types the CapabilityStatement declares so a capture UI can constrain its Location picker per form.

- **The Responses page, and the spool listing behind it: what came back, and what became of it** (2026-08-09). The capture UI's Responses page is every receipt this server holds, newest first - when it arrived, which form it answers, how many answers it carries, its receipt id, and which lifecycle state its file is in: `received` is the queue `d2w fhir forward` drains, `forwarded` means DHIS2 took it, `rejected` means DHIS2 refused it, each tinted by the shared status tokens. "Rejected" with nothing beside it is the one row a person cannot act on.

    **The receipt page is where the answers are, joined to the questions that were asked.** It is a route rather than a dialog, so one receipt is a link somebody can be sent, and it reads three documents to answer one question: the stored `QuestionnaireResponse` for the answers, `/spool` for the lifecycle and the import report, and the served `Questionnaire` for the questions - in that form's own order, each with its enclosing groups, which is what turns a disaggregated cell from `Fixed, <1y` into `Immunization / BCG doses given - Fixed, <1y`. Under all of it, a collapsible raw view of the stored resource - everything above is this UI's reading of that document, and a reading can be wrong in a way that is invisible until the bytes are on screen. The join itself is a pure function (`joinAnswersToQuestions` in `lib/receipt.ts`) tested against the same `$generate` fixtures the fill side round-trips through, including the missing-form degradation, and the browser suite drives the row click, the deep link, and the keyboard activation.

A drained receipt also keeps reading back - `GET /QuestionnaireResponse/{id}` answers it in whatever state it is in, because forwarding must not expire the id a client was handed at capture time. **And `GET /spool` is the one endpoint that is deliberately not FHIR**: it serves the receipt *envelope* - the instant the facade accepted the submission, the form kind it was validated as, the warnings it recorded, the lifecycle state, the DHIS2 import report behind a rejection - and none of those are QuestionnaireResponse elements. Two could be forced into `meta` and an `ImportSummary` could be bent into an `OperationOutcome`, but that spreads one record across a resource, a tag system no IG publishes, and a second operation, and the import counts still have nowhere honest to go. So it is typed JSON at a fixed one-segment lowercase path - which no PascalCase FHIR resource type can collide with - mounted with `/metadata` ahead of the read catch-alls.

- **`d2w fhir serve --ui`: the facade grows a browser, on the same port it already answers on** (2026-08-09). The header carries a reachability light over `/metadata` and, behind it, what the server said about itself, because a UI pointed at a stale `--live` process and one pointed at a freshly compiled IG look identical until you read the conformance document.

    **Mount order is the whole engineering problem, and it cuts both ways.** Starlette matches in registration order and the facade's read routes are catch-alls - `/{resource_type}` claims every one-segment path, `/{resource_type}/{resource_id}` every two-segment one. Placed first it swallows `/metadata` and every Bundle. - **`d2w fhir serve`: `Questionnaire/{id}/$generate` fills a served form, and the answer posts straight back** (2026-08-09). `GET|POST [base]/Questionnaire/{id}/$generate` answers one served form with a synthetic `QuestionnaireResponse`: every question answered with a value its own type, bounds, and terminology binding admit, wrapped in the context its form kind's response profile requires. The invariant it is built around is a test rather than a claim - **generated output POSTed back to this server's own `/QuestionnaireResponse` answers 201** - held per form kind (aggregate, event, tracker event), in both store modes, and under `--strict-codes`, whose exactness is what forces a generated coding to be the concept code the contract asks for rather than one of the lenient fall-back spellings. Two things follow. A capture UI gets its "fill with test data" button by calling one endpoint and shipping the answer to the endpoint it was already posting to. And a stress corpus becomes an API loop: `d2w fhir generate load-set` writes one to disk, `$generate` hands one out per request.

    **It is deliberately not SDC's `$populate`.** `$populate` means fill this form from real context about a real subject; `$generate` invents its data, and answering `$populate` with invented values would mislead every client that knows what it means. So it is a custom operation with its own artifact: the `foundation` target emits `foundation/d2-generate-operation.fsh`, a `D2GenerateOperation` OperationDefinition (`kind #operation`, `code #generate`, `resource #Questionnaire`, `instance = true` with `system` and `type` false, `affectsState = false` so a GET is legal, one optional `integer` `seed` input and a `QuestionnaireResponse` `return`), published under the IG canonical and named by `/metadata` on the **`Questionnaire` resource entry** - where R4 puts an instance-level operation, as against `$translate`'s type-level `rest.operation`. The IG's own `D2CaptureServer` stays silent about it on purpose: that statement is `kind #requirements`, and a server that only receives captures is still conformant.

    **The generator reads the capture index backwards.** `synthesize.py` builds the response from the very `CaptureIndex` the validator checks a submission against - the same `value[x]` element per question, the same `minValue` / `maxValue` bounds, the same `repeats`, the same `answerValueSet` binding resolved through the same `CodingResolverSet` - so a rule cannot be enforced on receipt without being honoured on generation. Coded answers are real concepts of the served CodeSystem, never invented, and a question bound to terminology this project never published is left unanswered rather than answered with something that would only make the server warn about its own output. One route serves both store modes: a live store holds the same compiled-shape Questionnaires and CodeSystems, so nothing about generation branches on `--live`.

    **`seed` makes a call reproducible**, on the query for GET or in a `Parameters` body for POST, as the R4 `integer` the operation declares (`0..2147483647`; anything else is a 400 OperationOutcome). Same form, same seed, same bytes. A call naming no seed is answered from one the server drew, and that is not a lesser mode, because **the seed comes back on the response** - as `QuestionnaireResponse.identifier` under `{canonical}/id/generate-seed`, which is R4's own element for a response's business identifier, needs no out-of-band header, and survives the post into the stored receipt. A corpus generated last week regenerates exactly by reading the seeds off it.

    Two facts a compiled `Questionnaire` cannot carry take documented rules rather than guesses. The data set's **period type** is read off a served example response answering the same form - a compiled IG ships its `Usage: #example` instances, and each aggregate one states the real type on its `D2Period` - and falls back to **`Monthly`** when the store holds none, which is every `--live` store; whichever type is decided, the response carries the newest *completed* period of it, so the value moves with the calendar and with nothing else. And **`TRUE_ONLY` is indistinguishable from `BOOLEAN`** at the item type, so both generate either value - a generated `false` against a `TRUE_ONLY` element is a value the form admits but the instance would not store. A tracker event's tracked entity and enrollment are shaped synthetic UIDs naming nothing on any instance, which is what makes that form kind generatable at all: the capture contract checks the shape of those identifiers, not their existence. A Questionnaire the server does not hold is a 404 OperationOutcome; one it holds but cannot read as a capture form is a 422 saying which.

- **`d2w fhir forward`: the capture spool drains into DHIS2, and the loop closes** (2026-08-09). `d2w fhir generate` writes the guide, `d2w fhir serve` turns it into a form and stores what a client fills in, and `d2w fhir forward` is the last leg: it reads every receipt out of `.serve/responses/received/`, translates it through `dhis2w_fhir.conversion` into the `/api/dataValueSets` envelope or the `/api/tracker` event its form kind reports as, and posts it. **DRY RUN IS THE DEFAULT**, and it is not a local simulation: every payload goes to the real endpoint on the real instance under that endpoint's own validate-only mode - `dryRun=true` on `/api/dataValueSets`, `importMode=VALIDATE` on `/api/tracker`, the two v42 spellings taken from the generated OpenAPI because the endpoints genuinely differ - so DHIS2's own rules grade the whole spool while nothing is written and no receipt moves. The terminal opens and closes with a DRY RUN banner naming `--import` as the way to commit, and the summary table says `mode: DRY RUN (validate only)` between them.

    **One client, six narrated steps**: read the spool, read the published guide (`ig/fsh-generated/resources` merged with `ig/input/resources`, the same two trees the facade serves), read the value types, translate, post, file. The value-type read is one id-only `/api/dataElements?fields=id,valueType&filter=id:in:[...]` over the data elements the published forms bind, and it is there for the one fact the compiled IG cannot carry: R4 spells DHIS2's `BOOLEAN` and `TRUE_ONLY` as the same `#boolean` item type, so without it a `TRUE_ONLY` question would be written the way `BOOLEAN` is. One POST per response, deliberately - DHIS2 answers a bundle with one report for the bundle, and a spool whose receipts move individually needs one answer each. Every event post carries `importStrategy=CREATE&async=false`, because a translated event carries no DHIS2 uid and the synchronous mode is what makes the answer the import report rather than a job to poll.

    **A DHIS2 refusal is an outcome, not an error, and it keeps every word DHIS2 said.** Both endpoints report one as `409 Conflict`, so it is recorded against that response instead of taking the run down; anything the error carries no JSON object for - an authentication failure, an unreachable instance - is about the run and is still raised. The two endpoints do **not** agree on the shape: `/api/dataValueSets` answers a `WebMessage` whose `response` is the `ImportSummary`, while `/api/tracker` answers the `TrackerImportReport` **bare**, with no envelope around it at all - so each family recognises its own report by the fields only that report carries rather than by assuming the envelope every other DHIS2 write has. Every row lands as a `ForwardImportIssue` (`error_code`, `subject`, `message`) whichever family named it - `response.conflicts[]` for aggregate, `validationReport.errorReports[]` for tracker - with the endpoint's own generated `ImportSummary` / `TrackerImportReport` riding alongside untouched.

    **Rejections roll up by cause.** DHIS2 states a rule once and then names every object that broke it, so `202 rejected` is usually three causes. `ForwardReport.rejection_reasons` groups them by error code plus the message with its quoted identifiers generalised away - `Event OrganisationUnit: \`ImspTQPwCqd\` and Program: \`IpHINAT79UW\`, do not match.` and the same sentence about another pair are one cause - counting each response once per distinct cause it met. The rollup renders on the terminal in both the condensed and `--details` views, opens the written report as a `Responses | Code | What DHIS2 said` table, and `--details` gains a Why column carrying each response's first reason truncated with a `(+N more)` count.

    **With `--import` the spool becomes the ledger** the `received/` name was chosen for. An accepted receipt is renamed into `.serve/responses/forwarded/`, a rejected one into `rejected/` beside an atomically written `<id>.report.json` holding its import outcome, and a **conversion-refused** one stays in `received/` untouched - the fix for it is in the guide or in the data, so the same command is the retry once that is fixed. The terminal states the distinction in its own closing line each way round: a DHIS2 rejection points at the import summary, a translator refusal points at the guide.

    `[serve] strict_codes` is the default coded-answer dial, so a project that captures strictly forwards strictly without stating it twice, and `--strict-codes/--no-strict-codes` reaches all three levels from the command line. The condensed terminal writes every response's outcome to `reports/fhir-forward-report.md` grouped by what became of it, with one counted hint; `--details` prints the per-response table instead, and `--json` carries the whole `ForwardReport` on stdout with the import summaries in it. `fhir_forward` joins `fhir_validate` as the plugin's second MCP tool, `dry_run` defaulting to True so the tool an agent reaches for first cannot change the instance. The scaffolded Makefile gains `make forward` and `make forward-import` (`d2w fhir init --refresh` adds them to an existing project). `ForwardReport`, `ForwardOutcome`, `ForwardOutcomeKind`, `ForwardImportOutcome`, `forward_responses`, `SpooledResponse`, `read_received_responses`, `move_to_forwarded`, `move_to_rejected`, `CompiledArtifacts`, `load_compiled_artifacts`, and `build_project_context` are part of the `dhis2w_fhir` package surface. Phase A of the conversion layer is shipped; what stays open is only which carrier phase B lifts the contract into.

- **`d2w fhir`: the identity stem is configurable - `[generate.naming] source = "id" | "code-or-id" | "code"`** (2026-08-08). One resolved segment per DHIS2 object - the **identity stem** - drives its FHIR resource id, its canonical URL, its file name, and its FSH artifact name, and `source` picks where the stem is read from: `"id"` (the default) takes the DHIS2 id verbatim, `"code-or-id"` takes the object's code when it can serve and falls back to the id with one aggregate note per surface, and `"code"` takes the code always, refusing the run through `CodeStemError` - a one-line error naming the offenders and the two ways out (fix the codes in DHIS2, or use `code-or-id` while migrating) - before a single file is written. Every naming surface resolves through the one `resolve_identity_stems` call per selection: option sets (the CodeSystem/ValueSet/ConceptMap triple of one set shares one stem), categories, organisation units (`registry/Organization-<stem>.json` / `Location-<stem>.json`, both resource ids, `partOf`, `managingOrganization`), questionnaires (`data-sets/<stem>.fsh`, `event-programs/<stem>.fsh`, `tracker-programs/<program stem>/<stage stem>.fsh`, the `Questionnaire-<stem>` ids and canonicals), examples (`examples/<target stem>-<n>.fsh` and every `Location/...` reference), and pages (`Questionnaire-<stem>-intro.md`, `Organization-<stem>-intro.md`, the artifact links). "Can serve" is the R4 `id` bar plus the surface's stem budget - the 64-character id limit for a bare stem, tighter where naming tokens spend characters - plus uniqueness among the surface's selected peers, a code equal to a peer's id included; underscores disqualify, so DHIS2's own demo codes (`OU_525`, `DS_359711`) can never serve, and nothing is ever truncated - an over-budget code falls back or refuses. Identity changes, data does not: the DHIS2 id and code stay as identifier slices on every resource, and the data identifiers inside an instance example never move with the source. Flipping the mode deliberately re-identifies the IG - a whole-project migration switch, so an instance team can move toward real codes incrementally and see the progress: under `code-or-id` the filesystem itself shows which objects have earned a readable name. `d2w fhir validate` previews all of it, scope-aware: `code-stem-fallback` (warning, what code-or-id semantics fall back on) and `code-stem-refusal` (error when `source = "code"`, parity-tested against the generate refusal) over the six naming surfaces, and the code coverage line now reads "selection objects whose code can serve as an identity stem". There is no name-sourced naming: DHIS2 names have no rules, are unstable, and are localized, so a name is not an identity source.

- **`d2w fhir validate`: severity means build impact on the configured IG** (2026-08-08). The run resolves the configured selection into an emission scope through the same selection semantics `generate` uses - five id-only reads, announced as the second of its now five steps - and every finding carries the verdict as `scope`: `selection` for objects the configured build emits, `instance` for the rest. An **error** is a build-aborting `<` code on an in-scope identifier surface, exactly the codes `d2w fhir generate` refuses through the shared predicate, and the only findings that gate exit 1; a **warning** is an in-scope degradation the build survives (a code falling back to the UID, a name malforming its page); an **info** is the same defect out of scope - instance hygiene, the code-migration watchlist. Measured on the Lao national instance this turns 4,062 findings with 35 "errors" (one of which could really abort a build) into 1 error, ~60 warnings, ~4,000 infos. The terminal summary gains a `selection findings` split and a `code coverage` line (`34/61 (selection objects with slug-safe codes)` - in-scope objects whose code meets the R4 `id` bar the new `usable_code_stem` predicate states, the number the UID-to-code naming migration watches); the rollup splits by (severity, scope, category) with the instance rows dimmed and the selection rows first within each severity; the passing line reads `passed: N selection warning(s), M selection info(s), K instance finding(s); ...`; and the md, csv, and pdf reports carry a Scope column on every row plus the selection split and coverage in their summaries. `ValidationScope`, `CodeCoverage`, `SurfaceCodeCoverage`, and `usable_code_stem` are part of the `dhis2w_fhir` package surface. `d2w fhir validate` still runs without a `fhir.toml`: with no project every selection table is empty, which selects everything, so the whole instance grades as on the build path.

- **`d2w fhir serve`: a taken port is one line, refused before the banner** (2026-08-08). The command binds the address once with `SO_REUSEADDR` - the option uvicorn itself sets - and releases it, so a port something else holds (typically 8080, where a local DHIS2 stack lives) fails as `error: port 8080 on 127.0.0.1 is already in use (usually the local DHIS2 instance; set [serve] port in fhir.toml or pass --port)` with exit code 1, before the `starting ...` banner and before the lifespan loads a store. The window between that probe and uvicorn's own bind is accepted and covered: an `EADDRINUSE` out of the uvicorn run - raised, or reported as uvicorn's log-and-`sys.exit(1)`, which a re-probe of the address tells apart from its other failures - renders the same one-liner instead of a traceback. The lifespan log now reads `loaded the compiled IG at <root>: N resources across T types, M stored responses`, because ASGI lifespan startup completes before the socket is bound - a load statement is the honest one there, and readiness is the server answering.

- **`d2w fhir`: ConceptMaps and `$translate`, unique attributes as identifiers, and terminals that say the state rather than the firehose** (2026-08-08).

    **A ConceptMap per option set, and a server that answers over them.** The `option-sets` target writes one `ConceptMap-<id-stem><slug>-cm.json` beside every pair, into `ig/input/resources/concept-maps/` - its own directory, because a JSON sync deletes every file in its target it did not produce. Two groups per map take every emitted concept code back to the DHIS2 option UID under `{base}/id/option` and to the DHIS2 option code under `{base}/id/option-code`, `equivalence #equal` throughout because both name the same DHIS2 option, built from the same concept assignment the concepts are so a mapping can only ever name a concept the pair really holds. The scaffolded `sushi-config.yaml` gains the matching `path-resource` glob (`d2w fhir init --refresh` adds it to an existing project), and `$DHIS2-OPTION` / `$DHIS2-OPTION-CODE` join the alias family with their NamingSystem declarations. `d2w fhir serve` answers R4's type-level `GET /ConceptMap/$translate?system&code[&targetsystem]` over the same store in both compiled and `--live` mode, replying with a `Parameters` resource carrying `result` plus one `match` per mapping - `equivalence`, the target `concept` as a Coding, the `source` map - or `result` false with a `message` naming what was not found. The operation is declared at `rest.operation` in `/metadata`, and only when the store actually holds a ConceptMap, because `/metadata` never advertises what the store cannot answer.

    **A unique attribute's values are identifiers.** DHIS2 marks an `Attribute` `unique`, and that flag is the only trustworthy signal that a value names its object rather than annotating it - on play 2.43 exactly three of eleven attributes are unique, while `PEPFAR_ID` and `NGOID` read like identifiers by name and are not. The `/api/attributes` join reads `unique` beside `code`, so it costs no extra request, and a unique value leaves the `D2AttributeValue` extension for the resource's `identifier` list under `{base}/attribute/{attributeUid}` - on the Organization and the Location, on both halves of an option set's and a category's pair, and on a Questionnaire. The namespace keys on the attribute UID because a DHIS2 attribute code may hold spaces and a system URI may not, and the identifier lands after the UID and code slices so a regenerate of an unchanged object stays byte-identical. Those per-attribute namespaces are declared **by convention rather than as NamingSystems**, deliberately: the foundation layer is built from `fhir.toml` alone and never reads an instance, so it cannot know which attributes exist, and a NamingSystem naming one that does not is worse than none.

    **`generate` refuses a build it knows will abort.** A DHIS2 code becomes an identifier value, and the IG publisher writes an identifier value into a table cell unescaped before strict-parsing the page it just wrote - so a `<` there kills the build in its final pass, after every resource has been rendered. `d2w fhir validate` already called that an error; generation now refuses the run before writing a file, naming the resource type, UID, name, and code and pointing at `d2w fhir validate` for the rest. The **whole run** is refused rather than the object skipped: skipping an option set leaves every Questionnaire that binds it pointing at a ValueSet nobody wrote. The gate reads the selection each target is about to emit, so an object the project does not publish can never refuse a run, and it covers every surface whose code reaches an identifier value - option sets, categories, organisation units, data sets, programs, and program stages. Only `<` refuses; `>` and `&` cost a malformed page rather than an aborted build and stay warnings. One predicate is shared with the validate finding, so the two cannot disagree.

    **The terminal says the state.** `d2w fhir validate` renders the summary table, a rollup row per (severity, category) with its count, every **error** individually - an error names the object that gates the build, and you should not have to open a file to see which - and one closing line pointing at `reports/fhir-validate-report.md`. Warnings and infos are counted rather than listed, because a national instance raises hundreds and the written report is where they are read one row at a time; `--details` puts every finding on the terminal too. Bare `d2w fhir generate` does the same for its notes: eight targets of aggregate notes bury the summary table, so they go to `reports/fhir-generate-notes.md` grouped by target with one counted hint on the terminal, and `--details` prints them inline. A solo target keeps printing its notes - one target's notes are short and you asked for that target by name - and `--json` is unchanged on both.

    **`[serve]` in `fhir.toml`.** Where a project is served from is a property of the project, not of the invocation: `host`, `port`, and `strict_codes` are stated once and `make serve` / `make serve-live` read them, which is what a developer whose local DHIS2 already holds 8080 needs. Precedence is flag beats table beats default, and `--strict-codes` gains a `--no-strict-codes` twin so all three levels are reachable from the command line. `make serve` and `make serve-live` are scaffold targets, and the FSH sweep is fully recursive so a nested generated file can never be left behind.

    **Two emit-time guards the profiles cannot express.** A form that would emit one `linkId` twice is refused whole by the questionnaire target - R4's `que-2` forbids it, and a response answering that linkId would name two questions at once - and the examples and pages targets now read the same filtered list, so nothing declares itself against a Questionnaire that was never written and no intro page narrates an artifact the guide does not hold. An `ORGANISATION_UNIT` answer naming a unit outside the org-unit selection is left unanswered rather than pointed at a Location the IG never publishes; a full run derives that selection from the org units it already read, and the solo examples target reads the UIDs alone, unpaged, under the registry's own filters - one small request rather than a second full walk.

    **`[generate] timezone`** names the IANA zone the instance's zone-less timestamps are wall-clock readings in (BUGS.md #62), stamping every emitted `dateTime` with the offset that zone stood at on that very instant, DST included; leaving it unset keeps the UTC reading.

    **The registry profiles get a worked example each.** The registry ships as JSON SUSHI never compiles, so `D2Organization` and `D2Location` published no example at all. `organization/registry-examples.fsh` is a curated `Usage: #example` pair drawn from the selection's own root unit - real UID, code, name, and level - so the publisher validates both profiles against data the instance really holds. It sits beside the profiles rather than under `examples/`, whose sync deletes every file it did not produce.

- **`d2w fhir`: one verb for the whole IG, and every long command narrates itself** (2026-08-08). Bare `d2w fhir generate` is the command: it runs all seven targets off a single pass over the instance - one client, one `fetch_live_ig_inputs`, **eight requests where the seven solo targets total twenty-five** (option sets read once instead of five times, `/api/attributes` once instead of four, the organisation-unit pagination once instead of twice) - with the foundation first because it reads nothing and the pages last because they narrate the rest. It reports **one summary row per target** rather than seven detail tables, each note labelled by the target that raised it, and `--json` dumps the whole `GenerateFullReport`. Naming a target still runs that target alone off its own client, which is what a tight edit loop on one directory wants. Typer-wise the bare run is a callback with `invoke_without_command=True`, so its `--progress/--no-progress` sits before the target name and each target carries its own after it.

    **Progress is a shared surface.** Every command with an instance behind it - the bare run, each target, `generate load-set`, `validate` - takes `--progress/--no-progress` and drives `dhis2w_core.progress`: a transient Rich spinner captioned `Step k/N: <label>` on a terminal, one plain `[k/N] label: summary` line per step when stderr is redirected, which is the form a CI log wants. The service layer only announces; the CLI owns `start`, the closing `finish`, and a `stop()` in a `finally`, so a writer error cannot leave a Live display's refresh thread running. Validate names the `/api/metadata` sweep for what it is and completes it with the collection and object counts; the organisation-unit walk captions its running page count; instance-sourced examples name each target as they read it.

    **Two channels, one rule.** Tables, notes, hints, and progress are narration and go to stderr; stdout carries the `--json` payload and nothing else, so `d2w --json fhir generate > report.json` is a clean document while the terminal still shows what ran. `--json` implies `--no-progress`: a JSON run builds no reporter at all, and stderr stays silent.

    **The flags say what they do.** `d2w fhir init --event-program <uid>` seeds the event-program table (matching `--data-set` and `--tracker-program`), and `--refresh` refuses any scaffold-content flag by name instead of silently ignoring it - a refresh reads identity off the project's own `fhir.toml`, which it never writes. `d2w fhir generate load-set --output-dir DIR` writes the corpus. `d2w fhir validate --output-dir DIR` names a **directory**, created if absent, holding `fhir-validate-report.md` / `.csv` / `.pdf`; `--details` lists the info findings individually; `--fail`/`--no-fail` is a pair, `--fail` being the default, and `--no-fail` drops the red `N error(s) found` line with the exit code. `--status` and `--code-source` are enumerated, so `--help` lists the choices and a wrong value is a usage error naming the flag. `d2w fhir serve` carries no `--profile` of its own - the root `d2w -p` is the one place a profile is named - and `--live` resolves it before the `starting <root> on http://host:port (ctrl-c to stop)` banner, so an unknown profile fails as a failure rather than under a line that already claimed the server was up.

- **`d2w fhir serve`: the generated IG runs as a FHIR read and capture facade** (2026-08-08). The guide states what a capture client sends; this is a server that accepts it. One verb over an existing project, shipped as a workspace member of its own - `dhis2w-fhir-serve`, installed by the `dhis2w-cli[serve]` extra, so an install that only generates FSH stays free of FastAPI and uvicorn and the command guards its import with an install instruction rather than an `ImportError`. Two modes over the same routes: the default loads the compiled `ig/fsh-generated/resources` merged with the predefined `ig/input/resources/{registry,terminology,categories}` tree SUSHI never re-emits, while `--live` builds the same read set straight off a DHIS2 instance through one client opened during startup and closed before the first request arrives - so no request path ever holds a DHIS2 connection. `GET /metadata` answers a `kind #instance` CapabilityStatement that `instantiates` the IG's own `D2CaptureServer` and narrows it to the types this store actually holds; `GET /{type}/{id}` answers the resource byte-faithfully, as the project published it; `GET /{type}?_id&url&identifier` answers a searchset Bundle whose `self` link echoes only the parameters applied, so `identifier={base}/id/program|<uid>` selects one program's stages against a running server exactly as the published guide documents it. A resource type outside the served set is refused as not supported rather than as not found, and every failure - raised, routed, or unexpected - answers as an OperationOutcome in `application/fhir+json`.

    **`POST /QuestionnaireResponse` is the one write**, validated against the served IG in phases where the phase that finds an error is the last one to run: the body and its R4 shape (400), then the `D2FormType` kind and the invariants that kind's profile pins, the questionnaire canonical and its item index, an aggregate response's `D2Period`, and finally every answer against that index (422). Inside a phase every issue is collected, so one round trip reports every problem at that level, each named by a FHIRPath `expression`. An accepted capture answers 201 with a `Location` header and an OperationOutcome carrying whatever the server had to interpret. Coded answers are lenient by default - the generated CodeSystem publishes both DHIS2 spellings of every option, so a client that sent the UID where the contract wanted the code has still named exactly one option, which resolves with a warning; a code the terminology holds under no spelling is a warning too, because an option added to the instance since the IG was compiled is a fact about the instance rather than a client mistake. `--strict-codes` turns both into refusals, `DEFAULT_STRICT_CODES` is the single flip point behind the setting, and two options matching one code is an ambiguity refused either way.

    **A stored response is a receipt.** It is the submission as it arrived, stamped with the id it is served under, held in memory and mirrored atomically to `.serve/responses/received/<id>.json`; reading it back says what was submitted, never what DHIS2 now holds, and the server says so in the accepted-capture outcome, in `/metadata`, and in its CapabilityStatement. Nothing here writes to DHIS2 - forwarding a receipt into an instance is the next phase, planned in `docs/project/fhir-conversion.md`, and `ls .serve/responses/received` is the pending count that phase will drain.

    **`d2w fhir generate load-set`** writes the corpus to exercise it: `--per-target` (default 25) synthetic `QuestionnaireResponse` documents per questionnaire target into `load/`, seeded from the target UID and the ordinal so a rerun over unchanged metadata is byte-identical. It is the volume twin of `generate examples` and deliberately not part of a full run - a load set is test data rather than IG source, so it sits beside `ig/` and the scaffold gitignores it alongside `.serve/`. An existing project picks both entries up from `d2w fhir init . --refresh`.

    **The JSON builders are the FSH emitters' twins.** `build_questionnaire_documents` and `build_data_dictionary_documents` return finished R4 documents with every name already absolute - exactly as SUSHI would have resolved it - through the very decisions the FSH path calls (`item_type`, `is_disaggregated`, `source_description`, `source_program`, the `FormKindProfile` identifier segments), and `test_fhir_questionnaire_parity.py` rebuilds the compiled questionnaires from committed source fixtures and asserts each equals the SUSHI output key for key. That is what makes `--live` byte-compatible with the compiled store, and it is the groundwork the conversion layer stands on.

    **Disaggregation is a data set's shape.** An event program's category combo describes the event's attribute option combo, not a per-question breakdown, so an event-kind response answers the flat `<dataElementId>` link id its Questionnaire asks - one answer per data element - while a data set's disaggregated element keeps one `<dataElementId>.<categoryOptionComboId>` cell per option combo. Both the response builder and the questionnaire emitter read the same `is_disaggregated`, so an example answers exactly the link ids its form declares.

- **`d2w fhir`: tracker programs publish as one Questionnaire per program stage** (2026-08-07). A `WITH_REGISTRATION` program is a sequence of visits rather than a single form, so it maps onto one `Questionnaire` per program stage rather than one per program. Each stage is filed under `tracker-programs/<programUid>/<stageUid>.fsh` - the only nested layout in the FSH tree, so a national instance's stages group by program on disk - with the stage UID as its `id`, `{prefix}PS_<stageUid>` as its name under the new `[generate.naming] program_stage` token, `subjectType = #Patient`, a title carrying both names ("Child Programme - Birth"), and three identifier slices: `$DHIS2-PS` / `$DHIS2-PS-CODE` for the stage and `$DHIS2-PROGRAM` for the program, which makes `Questionnaire?identifier={base}/id/program|<programUid>` select a program's stages on any FHIR server. The FSH sweep walks subdirectories to serve that layout, tracking produced files by relative path and removing a subdirectory it emptied; the JSON sweep keeps its flat whole-directory-ownership semantics. **A third selection table**, `[generate.tracker_programs]`, joins the other two and reads the same way - absent or empty selects every tracker program on the instance. The two program tables are read independently and each routes its UIDs to its own `programType`, so a program listed under the wrong table fails the run by name with a message pointing at the table that does select it, while a whole-instance sweep routes each program by its live `programType` and collects the types neither table maps into one aggregate note. `d2w fhir init --tracker-program <uid>` seeds the table offline, beside `--data-set` and `--event`.

    **The capture contract gains its third profile.** `D2TrackerEventResponse` describes one event of a stage, captured for an already enrolled patient: `D2FormType` fixed to `#tracker-event`, `authored` 1..1 (the event's `occurredAt`), `questionnaire` 1..1, and `subject` 1..1 restricted to `Reference(Patient)` as a **logical** reference - no `reference` element, `subject.identifier` 1..1 with its `system` fixed to `{base}/id/tracked-entity` - because the IG publishes no `Patient` instances and the tracked entity resolves against DHIS2. Two required extensions carry the rest of what DHIS2's add-event needs: `D2TrackerEnrollment` (a `valueIdentifier` under `{base}/id/tracker-enrollment`, tracker-scoped so a future enrollment kind keeps its own namespace) and `D2OrganisationUnit` (a `valueReference` to the unit's published `Location`, since `subject` is spent on the patient). There is no `D2Period` - an event happens at a moment. `D2CaptureServer` loops over the profile declarations, so all three ride `supportedProfile`. NamingSystem declarations extend to program stages (UID and code), tracked entities, and tracker enrollments; the last two declare the UID system alone, because DHIS2 gives a data object no `code` to declare one for.

    **Examples cover the third form kind both ways.** A synthetic tracker-event example draws its tracked entity and enrollment UIDs off the same seeded generator every other synthetic value comes from, so a regenerate stays byte-stable; an instance-sourced one reads `/api/tracker/events` per stage by `programStage` plus its `program` (DHIS2 demands the program beside the stage - BUGS.md #67) with `enrollment` and `trackedEntity` in the `fields` list. Every complete example declares `InstanceOf: D2TrackerEventResponse`, so SUSHI and the publisher validate the contract on every build; an event the instance answered neither UID for declares the base `QuestionnaireResponse` and is tallied in one aggregate note rather than dropped. The Forms page gains a "Tracker programs" section grouping each program's stages under its own heading, a stage's Questionnaire intro names its program, and the Capture page documents the third profile with a worked tracker event - subject, enrollment, organisation unit, authored - and says where a client obtains the two UIDs (`d2w data tracker enrollment list`, outside the guide's scope). Guide section `docs/guides/fhir-ig.md#data-set-event-program-and-tracker-stage-forms` and `#the-capture-contract`, architecture in `docs/architecture/fhir-plugin.md`, examples in `examples/v{41,42,43}/cli/fhir_generate.sh`.

- **`d2w fhir init`: the scaffolded IG is a uv project with a pinned toolchain** (2026-08-03). The FSH an IG publishes is a function of the d2w build that wrote it, so the scaffold now carries that build with the project. A new `pyproject.toml` declares `dhis2w-cli` and `dhis2w-fhir` on Python 3.13+ under the IG id normalised to a PEP 508 name (`dhis2.fhir.sldemo` becomes `dhis2-fhir-sldemo`), `uv sync` resolves them into `.venv`, and `uv.lock` is committed - `.gitignore` covers `.venv/` and deliberately not the lock. `[tool.uv.sources]` points `dhis2w-fhir` at the `packages/dhis2w-fhir` subdirectory of this repository on `main` until its first PyPI release, which is what the lock pins to a concrete commit; `dhis2w-cli` resolves from PyPI. `D2W` defaults to `uv run d2w`, so every make target runs the pinned build, with the checkout and `uvx --from` invocations kept as escape hatches. `make refresh` additionally runs `-$(MAKE) validate` between `generate` and `sushi`: a full rebuild wants fresh reports out of the instance, and validate exits 1 on instance code errors by design, so the leading dash keeps the rebuild going while every other step still stops the chain. Guide section `docs/guides/fhir-ig.md#pinned-toolchain`.

- **`d2w fhir init`: the scaffolded Makefile gains `make refresh`** (2026-08-03). One target for the full force-refresh a from-scratch review wants: `clean-all` (build output, terminology cache, and the package cache volume), `upgrade` (rebuild the docker image with `--pull --no-cache` for the latest SUSHI + IG publisher), `generate`, the fast `sushi` gate, then the full publisher `build`. Each step runs through `$(MAKE)` so the chain stops on the first failure. Documented in the scaffolded-Makefile table of `docs/guides/fhir-ig.md`.

- **`d2w fhir`: the published IG is a complete capture contract** (2026-08-02). A third party building QuestionnaireResponses against the generated forms needed the source to answer four questions the guide did not: what a valid response looks like, which questions are mandatory, what range a numeric answer may take, and how each answer is spelled. Four additions close all four. **Two QuestionnaireResponse profiles** land in `foundation/d2-responses.fsh` - `D2AggregateResponse` pins `D2Period` 1..1, `D2FormType` 1..1 fixed to `#aggregate`, `questionnaire` 1..1, and `subject` 1..1 restricted to `Reference(D2Location)`; `D2EventResponse` pins `D2FormType` 1..1 fixed to `#event` plus `authored` 1..1 and the same questionnaire/subject rules. Both follow the `[generate.naming]` prefix and the `[ig] status` dial, and the slice names are the extension names, so an instance addresses them exactly as the examples already did. **Every generated example declares one of them** as its `InstanceOf` instead of the bare resource, which turns the examples into a contract check: SUSHI and the IG publisher validate each one against its profile on every run, so a profile that stops describing what generation produces fails the build. `foundation/d2-capture-server.fsh` adds the `D2CaptureServer` CapabilityStatement (`kind = #requirements`, so R4 forbids `software` and `implementation`): one `create` on `QuestionnaireResponse` with both profiles as `supportedProfile`, plus `read` and `search-type` on `Questionnaire`, `CodeSystem`, `ValueSet`, `Location`, and `Organization`. R4 makes `CapabilityStatement.date` mandatory, so it takes a pinned literal - a generated timestamp would rewrite the file on every run, the same reason the NamingSystem declarations pin theirs.

    **Required questions now come off the data set.** `compulsoryDataElementOperands` is fetched with the rest of the projection and read at the grain DHIS2 states it: an operand naming a data element alone makes the whole question `required`, every disaggregated cell of it included, while an operand also naming a category option combo makes only that one cell required. Category option combo child items carry their own `required` flag for that reason. **Numeric bounds are emitted** as the standard `minValue` / `maxValue` extensions for the value types that *are* a constraint - `INTEGER_POSITIVE` from 1, `INTEGER_ZERO_OR_POSITIVE` from 0, `INTEGER_NEGATIVE` up to -1, `PERCENTAGE` 0 to 100, `UNIT_INTERVAL` 0 to 1 - typed `valueInteger` on an integer item and `valueDecimal` on a decimal one, on plain questions and disaggregated cells alike. `INTEGER` and `NUMBER` carry none because DHIS2 bounds neither, and a guard test asserts every `BOUNDS_BY_VALUE_TYPE` key is a member of the generated `ValueType` enum across v41/v42/v43, beside the one that already guards the item-type table.

    **A sixth site page, `capture.md`,** is the prose half. It states the single-response-per-request rule, then walks an aggregate response and an event response step by step against forms this project actually selected: the canonical URL rule, the `D2Period` extension worked with a real ISO period resolved through `parse_period` from the pinned reference date, the `D2FormType` code, the `subject` reference to a real organisation unit off the registry, the two `linkId` grammars (`<dataElementId>` and `<dataElementId>.<categoryOptionComboId>`), the required rules, and `authored` plus the DHIS2 event status map for events. It closes with an answer-typing table over every DHIS2 value type, the coded-answer rule (`valueCoding.system` is the option set's CodeSystem canonical, `code` is the concept code exactly as generated, both DHIS2 identifiers readable off the concept properties), and the validate-before-you-send workflow linking both profile pages and the CapabilityStatement. - **`d2w fhir generate examples`: example QuestionnaireResponses for every generated form** (2026-08-02). A generated `Questionnaire` says what a DHIS2 form asks; a `QuestionnaireResponse` says what an answer to it looks like, which is what an implementer reads before writing an integration. The items **mirror the questionnaire**: section groups nest their questions and a disaggregated data element nests one child per option combo under `<deUid>.<cocUid>`, which is exactly a DHIS2 data value's `(dataElement, categoryOptionCombo)` key. Answers are typed from the data element's `valueType` - integers to `valueInteger`, `NUMBER` / `PERCENTAGE` / `UNIT_INTERVAL` to `valueDecimal`, `BOOLEAN` / `TRUE_ONLY` to `valueBoolean`, the temporals to `valueDate` / `valueDateTime` / `valueTime`, an option-set-bound question to a `valueCoding` into that set's generated CodeSystem carrying whichever concept code `concept_code_source` selects - and anything that will not cast falls back to `valueString` with one aggregate note per run rather than being emitted invalid.     `[generate.examples]` takes `per_target` (default 1; `0` disables the target, which still sweeps its directory clean) and `source`, and **`source` defaults to `synthetic`** because an example is published. Synthetic mode calls no data endpoint at all: `build_synthetic_responses` seeds a `random.Random` with the leading 64 bits of `sha256("<targetUID>:<n>")` - never Python's per-process-salted `hash` - so a regenerate is byte-identical across machines and interpreter restarts, every question is answered, every option combo of a disaggregated element is filled, `TRUE_ONLY` is always `true`, and an option-set-bound question draws a real concept from the set the IG publishes. The one value that moves with the calendar is the anchor: a data-set example takes the newest completed period of its period type, and its temporal values are drawn from that window. `source = "instance"` reads the server instead - data sets walk the six newest completed periods against `GET /api/dataValueSets` (root organisation unit, `children=true`) and stop at the first one holding values, grouped by the DHIS2 reporting key `(orgUnit, period, attributeOptionCombo)` richest-first; event programs read `GET /api/tracker/events` ordered `occurredAt:desc`, tolerating both the `instances` and `events` envelope keys. Instance-sourced examples embed real captured values into a document you are about to publish, which is right for a demo server and wrong for a production one - hence the default. A target the instance holds nothing for is one aggregate note, never a failure.

    `dhis2w_fhir.period.recent_periods(period_type, count, today)` is the new inverse of `parse_period`: the most recent periods of a type whose end date is already past, newest first, for all twenty-three registered types. It is built *on* the parser rather than beside it - each type declares only how its ISO strings are spelled for a year, and the parser decides which of those exist and what dates they cover - so the two cannot drift apart, and the round-trip is asserted per type.

    The DHIS2 `valueType` mapping is now complete and guarded. `ITEM_TYPES_BY_VALUE_TYPE` carries an explicit entry for all 28 members of the generated `ValueType` enum across v41/v42/v43 (`TRACKER_ASSOCIATE` is v41/v42 only), and a test reads those three enums and fails when any member has no entry - so a codegen refresh that introduces a new DHIS2 value type becomes a deliberate mapping decision instead of a silent `string`. New and changed rows: `URL` to `url`, `FILE_RESOURCE` and `IMAGE` to `attachment`, `AGE` to `date` (DHIS2 stores the date of birth; the age is rendered from it), `GEOJSON` to `text`, `COORDINATE` to `string`, and explicit `string` entries for `LETTER` / `PHONE_NUMBER` / `EMAIL` / `USERNAME` / `REFERENCE` / `TRACKER_ASSOCIATE`. `MULTI_TEXT` is option-set bound by definition and now emits `repeats = true`, which is the whole of what it means - DHIS2 stores a comma-separated list of option codes against one data element, and an example response answers such a question once per code. `D2DE_CS` gains a `domain` concept property valued `#aggregate` or `#tracker` from the data element's `domainType`, declared under the same `<base>/property/<code>` URI scheme and omitted entirely when the instance sends none. The synthetic synthesizer honours the new types: a `URL` answers an `example.invalid` URI naming the example, `AGE` a seeded date of birth, `COORDINATE` a seeded `[longitude,latitude]` pair, `MULTI_TEXT` two distinct concepts - and `FILE_RESOURCE`, `IMAGE`, and `GEOJSON` are left unanswered with one aggregate note, because an invented attachment or catchment polygon misrepresents the form.

    A data set's data elements are ordered by name. `dataSetElements` is a Java `Set` with no sort order and DHIS2 serialises it differently on every request (BUGS.md #63), which made `generate questionnaires` rewrite an unchanged data set's file on every run and made the example responses answer their questionnaire's items out of order - a FHIR validator error. Ordering the members by name and UID at the fetch boundary fixes both; section membership is joined by UID and keeps the section's own sort order, which DHIS2 does hold, and event programs are untouched because `programStageDataElements` is genuinely ordered.

    Page titles are HTML-escaped. `fhir2.base.template` pastes a resource's FSH `Title:` into the breadcrumb unescaped and the publisher then strict-parses the result, so a DHIS2 name holding `<` - the play 2.42 data set "Mortality < 5 years by gender" is a real one - aborts the build with `Unable to Parse HTML`. `names.page_text` escapes `&`, `<`, and `>` on the page-facing `Title:` / `Description:` lines of every generated instance (Organization, Location, Questionnaire, QuestionnaireResponse, NamingSystem); the element-level `* title` / `* name` keep the DHIS2 text verbatim, because those are data rather than page furniture.

    `d2w fhir validate` gains `template-hostile-name`, a warning on any metadata object whose **name** holds `<`, `>`, or `&`. It runs in both passes at warning severity in either code source, because it is about the pages the IG publishes rather than about what generation reads: the sweep covers every metadata object, and the deep option-set pass covers option names, which the sweep excludes and which land in concept displays and page tables. The offending name prints through the same renderer the code column uses, so an invisible character in it is visible. The warning exists because escaping is only half a fix - the page metadata generation controls is escaped, but a resource's own `title` / `name` elements stay byte-true DHIS2 data, so `Questionnaire-<uid>.change.history.html` still renders malformed for such a name. Substituting entities into the data would make the IG disagree with the instance about what the data set is called; the warning puts the fix in DHIS2 instead.

### MCP tool annotations

- **Every MCP tool advertises a `readOnlyHint` annotation.** The full `dhis2-mcp` server stamps each
  of its ~315 typed tools with `readOnlyHint` (reads `True`, writes `False`), derived at build time
  from the same read/write name classifier the read-only middleware already uses; the router hints its
  `search_tools` read-only and leaves `call_tool` (the write chokepoint) unhinted. A host that honours
  the annotation — e.g. one that skips its per-action write confirmation for read-only-hinted tools —
  gets frictionless reads while writes still prompt, with no per-tool configuration. A hand-set hint is
  never overwritten, and the hint is present regardless of the `DHIS2_MCP_READONLY` switch. Because the
  name classifier now drives an always-on hint that a client may use to skip confirmations, a
  registry-wide guard asserts no write tool is ever hinted read-only.

Hardening release driven by a multi-pass audit. Eleven PRs landed across CLI behaviour, MCP safety, client robustness, docs accuracy, CI coverage, and workspace plumbing. No new product surfaces — every change tightens an existing one.

### Client + plugins

- **`Dhis2Client(version=...)` raises on server mismatch.** Pinning v43 against a v42 server used to silently bind the v43 generated tree on top of v42 wire payloads, round-tripping renamed/added fields wrong. `connect()` now compares the reported `/api/system/info` version's major against the pin and raises a new `VersionPinMismatchError` (subclass of `UnsupportedVersionError`). Opt out with `allow_version_mismatch=True` if you've audited the schema overlap yourself (#339).
- **Cross-origin canonical-URL redirects require DHIS2 confirmation.** `_resolve_canonical_base_url` used to follow `play.dhis2.org` → `play.im.dhis2.org` migrations but would also follow an SSO IdP redirect, leaving subsequent `/api/...` calls pointed at the IdP host. Cross-origin redirects are now probed against `/api/system/info` (DHIS2 always returns JSON regardless of auth state) before being adopted; IdP redirects fall back to the original URL (#334).
- **OAuth2 authorization-code exchange wraps failures into `OAuth2FlowError`.** Used to leak raw `httpx.HTTPStatusError` on bad client_secret / redirect mismatch / DHIS2 OAuth2 misconfig. Now mirrors the refresh path: RFC 6749 `error` / `error_description` re-emitted when DHIS2 returns them, or a truncated body snippet otherwise, plus a common-causes hint (#341).

### CLI

- **`dhis2 --profile NAME ...` applies before plugin discovery.** `app = build_app()` ran at module-import time, freezing the plugin tree at whatever the default profile pinned (typically v42) before argv was parsed. `dhis2 --profile v43p --version` would print `plugin tree: v42`, and v43-only commands stayed hidden. `main()` now pre-scans `sys.argv` for `--profile` / `-p` / `--profile=NAME` and sets `DHIS2_PROFILE` before building the app (#333).
- **`docs/cli-reference.md` regenerates correctly** — the typer-docs introspection used by `make docs-cli` needs a module-level `app` instance, which #333 had removed. Restored the module-level `app = build_app()` with a comment clarifying it's only consumed at docs-build time; the entry point uses `main()` which builds its own fresh app after the argv pre-scan (folded into #335).

### MCP

- **Per-call profile guarded against bound plugin tree.** A v42-booted server invoked with a v43-pinned profile used to parse v43 server payloads through v42 schemas silently. `dhis2w_core.profile.bind_version_tree()` is called once at `build_server()` time; `resolve_profile()` now raises `ProfileVersionMismatchError` with a restart hint (`Restart with DHIS2_VERSION=v43 dhis2w-mcp ...`) on any mismatched per-call profile (#338).

### Workspace + packaging

- **Root `pyproject.toml` switched to bare-workspace form.** The `[project]` table at the repo root was unused metadata that drifted on every release — dropped along with `[tool.uv] package = false`. `uv lock` removes the meaningless `dhis2-utils v0.1.0` entry (#332).

### Documentation

- **MCP single-major + filesystem-trust + stale claims.** `docs/mcp/index.md` now spells out that one running server targets a single DHIS2 major (per-call profile only swaps profiles within that major; `ProfileVersionMismatchError` enforces it). New filesystem-trust section covering `metadata_export(output_path)`, `metadata_diff(left_path)`, `customize_apply`, `apps_install_from_file`, `apps_snapshot` — unsandboxed local-path I/O, with recommendations for constrained cwd / container isolation. `docs/architecture/mcp.md` refreshed to show `resolve_startup_version()` + `_eager_rebuild_tool_return_types()` in the `build_server()` snippet. `docs/testing.md` drops the stale `Tracker / data values / analytics don't exist yet` claim (#335).
- **MCP parity claim softened.** `docs/index.md` previously read _'every CLI command has a matching MCP tool (and vice versa)'_ — reality: `dhis2 dev` / `dhis2 browser` / profile mutations are intentionally CLI-only. Replaced with _'most operational commands ship as both'_ + an enumerated exclusion list (#340).

### Testing + CI

- **Per-version smoke matrix.** New `tests/test_v{41,43}_smoke.py` (dhis2w-client, 8 tests) covers top-level imports, `build_auth_for_basic` dispatch, and `open_client` handshake binding the right tree. New `tests/test_v{41,43}_plugin_smoke.py` (dhis2w-core, 6 tests) verifies `discover_plugins("v{N}")` returns the full plugin set with v{N}-bound modules. Provides structural guardrails on hand-written v41/v43 trees that currently sit under coverage omits (#336).
- **Example matrix in nightly E2E.** The E2E workflow already runs `make test-slow` against a docker stack per DHIS2 major. Appended `make verify-examples` to the same matrix job so the ~150-example surface per version gets exercised nightly. `SKIP_BY_DEFAULT` entries (browser / OIDC / fixture-gap) still skip per the script's policy (#337).

### Workspace packages

### Migration notes

## 0.10.0 — 2026-05-12

### Architecture

- **Per-version subpackages everywhere.** `dhis2w_client.v{41,42,43}` and `dhis2w_core.v{41,42,43}.plugins.*` are now hermetic — a v43-specific quirk lands in `v43/plugins/...` alone without touching v41/v42. Three trees seeded from the v42 baseline (#253-#272).
- **Per-version `__init__.py` re-export surfaces.** `from dhis2w_client.v41 import X` now works directly, parallel to `from dhis2w_client.v42 import X` and `from dhis2w_client.v43 import X`. The top-level `dhis2w_client` shim still routes to v42 for backwards compat with PyPI consumers (#280-#282).
- **Per-version `dhis2w-core` helpers.** `cli_errors`, `cli_output`, `cli_task_watch`, `client_context`, `oauth2_registration`, `pat_registration`, and `token_store` all have v41 / v42 / v43 copies under `dhis2w_core/v{N}/`. Shared runtime state (`JSON_OUTPUT` ContextVar, `_console` Rich singleton) stays single-source via re-exports — only the type-signature surface diverges per version (#283-#285, #289).
- **Plugin discovery resolves the version from `DHIS2_VERSION` env when `profile.version` is unset.** Lets `make verify-examples DHIS2_VERSION=v41` correctly drive the v41 plugin tree without hand-editing every profile (#292).
- **Plugin retarget — all 47 plugin files per version-tree now import from their matching client subpackage** (`dhis2w_client.v{N}.*` + `dhis2w_core.v{N}.*` helpers + `dhis2w_client.generated.v{N}.*`). One hand-fix per version for genuine wire-shape divergence (#286-#288).
- **Top-level shim dropped from `dhis2w-core`-internal call paths.** Canonical imports go through `v{N}/`; the top-level remains as a PyPI-stable surface only (#271).

### v41 wire-shape adapters

- **OAuth2 round-trip reads `cid` (BUGS.md #39).** v41 wire shape names the client identifier `cid`; v42/v43 use `clientId`. `dhis2 dev sample oauth2-client` smoke test tolerates both, preferring v41-correct `cid` on the v41 plugin tree (#262, #292).
- **Dropped `oauth2-client-credentials` auth-scheme variant.** v41's OAS and runtime don't ship it; v42/v43 do (#264).
- **`SharingObject` retargeted to `generated.v41`** with a local `Status` stub for the v41-missing enum (#269).
